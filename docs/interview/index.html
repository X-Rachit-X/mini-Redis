Say

"Here's the life of one command. A single thread sits in epoll_wait. When a client's socket has data, I read up to 16 KB into that client's own input buffer."

"That buffer matters because TCP is a byte stream, not a message stream. One read can hold half a command or fifty of them. The parser answers 'complete', 'need more bytes' or 'invalid', and I keep parsing until no complete command is left. That's also how pipelining works."

"Each command is looked up in a hash table that gives its handler and how many arguments it takes. The data itself is a hash map from key to a std::variant, so a key has exactly one type."

"If the command changed data, it goes into the append-only log, and the log is written before the reply is sent, so a client never sees OK for something that isn't logged. Replies go into an output buffer, and if the socket is full I ask epoll to tell me when it's writable again."

The 5 KB bug

Goal: your best story. Measurement → surprise → root cause → fix → guard.

On screen: memory per key, drawn to scale

using Value = std::variant<std::string, List, Hash, SortedSet>;
//            sizeof(Value): 5088 bytes  →  88 bytes

class SkipList {
    ...
    std::mt19937 rng_;   // ~5 KB of state, inside EVERY value
};

Say

"This is my favourite part. I didn't assume memory was fine, I measured it: load a hundred thousand tiny keys and compare process memory before and after. It came out to about five kilobytes per key, for one-byte values."

"Every value is a std::variant of string, list, hash or sorted set, and a variant is always as big as its largest alternative. My sorted set contained a skip list, and the skip list held its own random number generator, a Mersenne Twister, which carries about five kilobytes of state. So every key, even a tiny string, paid for a generator it never used."

"I moved the generator to one shared static. That cut memory thirty times, to 175 bytes per key, within 2× of Redis. Then I added a unit test that fails if the per-key entry ever grows past 256 bytes, so it can't come back silently."

TipTell it as a story with a turn: "I expected X, measured Y." This is the answer to "tell me about a bug you fixed" and "how do you debug performance".

Deep dives

Each one: the question as they'll probably ask it, your spoken answer, what to draw, and the follow-ups that come next.

"Why single-threaded? Wouldn't threads be faster?"event loopHooked by: "a single thread with an epoll event loop"

Say

"Each command takes microseconds, because everything is in memory. The slow part is waiting on the network, and epoll does that waiting for thousands of sockets from one thread. So the CPU work is small and the waiting is shared."

"One thread also means no locks, no contention and no data races, and every command is atomic for free. INCR can never lose an update. My first version used a thread per client with a global mutex, and the mutex serialised every command anyway, so I paid for threads and got none of the benefit."

"The trade-off is one core, and a slow command like KEYS on a big database blocks everyone. Redis 6 kept command execution on one thread but moved socket reads and writes to I/O threads. If I needed more throughput, I'd do that or run several independent instances."

Follow-ups

  • "Level-triggered or edge-triggered?"Level. epoll keeps reporting a socket while data is waiting. I read one 16 KB chunk per event, which is fair across clients. Edge-triggered only fires on changes, so you must drain until EAGAIN or you hang.
  • "Why only enable EPOLLOUT sometimes?"A socket is almost always writable. If EPOLLOUT stayed on, the loop would wake constantly with nothing to do and spin at 100% CPU. I turn it on only when a send() couldn't finish, and off once the buffer drains.
  • "What if a client never reads its replies?"Its output buffer grows. Mine has no cap yet, which is a known gap. Redis disconnects such clients with client-output-buffer-limit, and that's what I'd add.

Draw

while (!stop) {
  n = epoll_wait(ep, events, 128, 100ms)
  for each ready fd:
    listen fd  → accept all, set O_NONBLOCK
    EPOLLIN    → read 16 KB → parse → run
    EPOLLOUT   → send the rest of output
  every 100 ms: expire keys
  every 1 s:    fsync AOF
}

One thread. No mutex anywhere in the server.

"What if a command arrives in two packets? How does pipelining work?"protocolHooked by: "Redis wire protocol", "TCP is a byte stream"

Say

"TCP only guarantees the bytes arrive in order. It doesn't keep message boundaries. So each client has an input buffer, and the parser looks at it and returns one of three answers: a complete command, 'incomplete, wait for more bytes', or a protocol error."

"The Redis protocol prefixes every value with its length, so I never scan through a value looking for a delimiter. I calculate where it ends. If those bytes aren't in the buffer yet, it's incomplete. That's also why values can contain anything, including newlines: it's binary safe."

"Pipelining falls out naturally: I loop over the buffer running every complete command, write the log once, and send all the replies in one send call. My unit test feeds the parser every possible prefix of a command and checks each one is 'incomplete', and the end-to-end test sends a command split across two packets with a pause in between."

Follow-ups

  • "What stops someone sending a 10 GB command?"Limits, same as Redis: at most 1 million arguments, 512 MB per argument, 64 KB per header line, 1 GB per client buffer. Past that, the client gets an error and is disconnected.
  • "Do you re-parse from the start when more data arrives?"Yes, which keeps the code simple. It only re-reads the small headers; bulk bodies are skipped by length, so the cost is per argument, not per byte.

"Why a skip list? Why not std::map?"data structuresHooked by: "a skip list that keeps a span on every link"

Say

"A sorted set needs insert, delete, and 'what's the rank of this member' or 'give me positions 10 to 20'. std::map gives log-time insert, but it can't tell you a position. std::distance walks one element at a time, which is linear."

"A skip list is a sorted linked list with express lanes on top. Each node gets a random height, so searches skip most nodes and take log n on average, with no rebalancing. Then each link stores its span, how many nodes it jumps over. Adding up spans along the search path gives the rank in log n. That's exactly what Redis does."

"Next to it is a hash map from member to score, so ZSCORE is constant time. In a micro-benchmark with 200 000 members, ZRANK was over three thousand times faster than walking a std::set."

Follow-ups

  • "How did you know the span arithmetic was right?"A randomized model test: 20 000 random adds, updates and removes with lots of equal scores, compared with std::set every 500 operations, for the full range, every rank and a sub-range. Plus AddressSanitizer for pointer bugs.
  • "How are ties ordered?"By score, then by member name, like Redis. Without a tie-breaker, equal scores would have no defined order.
  • "Worst case?"O(n) if the random levels came out terrible, but the probability is negligible. Balanced trees guarantee log n but need rotations, and still need extra counts for rank.

level 1:  head --(2)--> b --(2)------> d --> nil
level 0:  head -1-> a -1-> b -1-> c -1-> d --> nil

"What happens if it crashes in the middle of a write?"persistenceHooked by: "flushes the log and fsyncs it", "log written before the reply"

Say

"Every command that changes data is appended to the log in the same format clients send. On startup I replay it through the normal parser and command code."

"If the process dies halfway through a write, the file ends with half a command. On startup the parser says 'incomplete' at the end, and I truncate the file back to the last complete command and carry on. Garbage in the middle is different: that's real corruption, so I refuse to start rather than silently lose data."

"Durability is configurable like in Redis: fsync always, every second, or let the OS decide. write() only puts data in the OS cache, so a process crash loses nothing that was written, but a power cut can lose up to a second in the default mode."

"Two details I'm proud of. Expiry commands are relative, 'in 100 seconds', so replaying them tomorrow would be wrong. I log them as absolute timestamps instead. And compaction writes a new file, fsyncs it, then renames it over the old one. rename is atomic, so a crash leaves either the old file or the new one, never half of each."

Follow-ups

  • "Does the rewrite block clients?"Yes, mine is synchronous. Redis forks a child that writes the snapshot using copy-on-write memory while the parent keeps serving and buffers new writes. That's my next step.
  • "Why reopen the file after rename?"My file descriptor still points at the old file, which still exists while it's open. New writes would go into a file nobody reads.

                                   ^ truncate here

"How do expiring keys actually get deleted?"TTLNatural follow-up to the live demo's "SET session abc EX 5"

Say

"Two ways, like Redis. Lazily: every lookup goes through one find function that checks the expiry time and deletes the key if it has passed, so no command can ever see an expired key."

"Actively: ten times a second I remove keys nobody touches. I keep a std::set of expiry time and key, so the soonest key is always at the front. I only look at keys that have actually expired, capped at 200 per round so the loop stays responsive."

"Redis does it differently: it samples 20 random keys that have a TTL and repeats while a quarter of them were expired. That saves the memory of my index, but it's probabilistic. Mine is exact but costs more memory per key with a TTL."

Follow-ups

  • "Why wall-clock time and not a steady clock?"Expiry times are saved in the log and must mean the same moment after a restart. The trade-off: if the system clock jumps, TTLs jump too. Redis has the same issue.

   ^ now = 1300: remove a, x; stop at s

"Five kilobytes per key? How?"C++ / memoryHooked by: the opener and stage 05

Say

"std::variant stores its value inline, so its size is the size of its largest alternative plus a tag. My largest alternative was the sorted set, which contained the skip list, which had a std::mt19937 member. A Mersenne Twister keeps 624 words of state, about five kilobytes on 64-bit Linux. So sizeof(Value) was 5088 bytes, and every key paid that, even a one-byte string."

"I found it by measuring, not by reading code. I loaded 100 000 keys and compared the process memory before and after: about 490 MB. Then sizeof confirmed it. Making the generator a function-local static shared by all skip lists brought sizeof(Value) to 88 bytes and memory per key to 175."

Follow-ups

  • "Where do the remaining 175 bytes go?"96 for the entry itself, then the key string, the hash table node and its bucket pointer, and allocator overhead. Redis gets 93 by packing small values into compact encodings and using jemalloc.
  • "Is a shared static generator thread-safe?"Not in general, but the server is single-threaded, so only one thread ever calls it. If I added threads, I'd make it thread_local.
  • "Doesn't sharing it change behaviour?"No. Node heights only need to be random-looking, not independent per list. The fixed seed still makes runs reproducible.
  • "How would you shrink it further?"Store big types behind a pointer so the variant stays small, use small-string encodings, and a better allocator.

Rapid fire

Short answers for short questions. One or two sentences, then stop.

Why std::deque for lists?LPUSH and LPOP need constant time at the front. A vector shifts every element: over 1000× slower at 50 000 items in my benchmark.
Why std::variant instead of a map per type?A key can only have one type. With three maps, the same key could be a string and a list at once. Now TYPE and WRONGTYPE are correct by construction.
How do you shut down safely?The signal handler only sets a flag; that's all that's safe in a handler. epoll_wait returns EINTR, the loop sees the flag, then flushes and fsyncs the log.
What about SIGPIPE?Ignored, and every send uses MSG_NOSIGNAL. Otherwise one client disconnecting mid-reply would kill the server.
Why disable Nagle's algorithm?It delays small packets hoping to merge them, adding up to 40 ms to tiny replies like +OK.
How is it tested?32 unit tests including a randomized model test, 35 end-to-end tests over real TCP, all under AddressSanitizer and UBSan in GitHub Actions.
Why is KEYS dangerous?It walks every key on the only thread, so every other client waits. Production Redis users use SCAN instead.
What was the hardest part?The span arithmetic in skip-list insert. I didn't trust it until the randomized test agreed with std::set over 20 000 operations.
